# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RADIX is an offline-first LMS simulating an edge server (Raspberry Pi) in the Amazon: Go REST backend + React SPA. Content is uploaded locally, students consume it offline earning XP, and a DTN (Delay-Tolerant Networking) sync queue records transactions for opportunistic sync with a central server. Three roles: `admin` (professor), `student`, `guest` — all gated via a Bearer-token session + RBAC middleware.

Monorepo layout: `backend/` (Go module `radix-backend`), `frontend/` (Vite/React SPA), `config/docker/` (local DB container).

## Commands

### Backend (run from `backend/`)
```bash
go run ./cmd/server        # start the API server (:1323 by default)
go run ./cmd/seed          # seed demo data — separate command, NOT run automatically on server boot
go run ./cmd/flush         # empty every table (schema + migration record stay); -yes skips the prompt, -uploads also deletes uploads/
go build ./...             # compile check
go vet ./...               # static check
gofmt -l .                 # formatting check (no diff = clean)
```
No test suite exists yet. No `CGO_ENABLED` requirement — both DB drivers (`tursogo` for local-only mode, `libsql-client-go` for remote mode) are pure Go.

Hot reload: `air` (`.air.toml` only watches `*.go` files — editing `.env` requires manually restarting the `air` process, it will not pick up new env vars on its own). `.air.toml` sets `send_interrupt = true` / `kill_delay = "2s"` — without these air SIGKILLs the old binary on every rebuild, skipping fx's graceful-shutdown hooks.

### Test network (throwaway, everything in containers)
```bash
./testnet.sh                                      # recreate + wait + print URLs
./testnet.sh --three                              # 3 nodes, A->B->C forwarding
docker compose -f config/docker/testnet.yml down                # nothing survives
```
`testnet.sh` is the entry point: it tears down first (so it's repeatable), rebuilds, then polls each published port until the node answers — `up --detach` returns while the backends are still migrating and importing the seed zip, so a script that printed the URLs immediately would be lying.
Each node is db + backend + frontend. Only the backends (1323/1324/1325) and frontends (5173/5174/5175) publish ports — the databases are reachable only through their own backend. Nothing is persistent: sqld data and `uploads/` are tmpfs, no named volumes, and every start re-imports `seeds/radix-seed-backup.zip`, so all nodes begin identical and diverge from there. `SYNC_INTERVAL_SECONDS` is 15 instead of 60 so a change crosses while you're watching.

### Database (local dev)
```bash
cd config/docker && docker compose up -d     # starts a local sqld/libsql-server on :8080 (HTTP) / :5001 (gRPC)
```
The backend connects to this container by default (`TURSO_URL=http://localhost:8080` in `.env`). To reset local data: `docker compose down -v && docker compose up -d` (drops the container's volume) — remote mode keeps no local cache file, so nothing else to delete.

Multiple backend processes against the same remote sqld are fine to run concurrently now (no shared local replica file to corrupt) — but still avoid it for the usual reason (two processes racing the same session map / log persister is just confusing to debug).

sqlc + goose:
```bash
sqlc generate                                        # regenerate internal/database/dbgen from queries/*.sql
goose -dir internal/database/migrations turso "$TURSO_URL" status   # or use GOOSE_* env vars from .env
```

### Frontend (run from `frontend/`)
```bash
bun install && bun run dev   # SPA on :5173, proxies /api to the backend port (VITE_API_PORT)
bun run build                # tsc + vite build
```

## Architecture

### Backend: dependency injection with uber/fx

`cmd/server/main.go` is the sole composition root — it's the only place that wires concrete types together. Everything else depends on interfaces or receives its dependencies as constructor params; nothing else imports `internal/store` directly.

- `internal/auth` and `internal/handlers` each define their **own** small `Store` interface listing only the methods they actually call (e.g. `auth.Store` has 5 methods, `handlers.Store` has ~19). `*store.Store` satisfies both by structural typing — it is never changed to accommodate this.
- In `main.go`, `store.New` is registered once via `fx.Annotate(store.New, fx.As(new(auth.Store)), fx.As(new(handlers.Store)), fx.As(fx.Self()))` so the same instance is exposed as both interfaces plus its concrete type.
- `auth.New(s Store) *Auth` and `handlers.New(s Store, logBuf *middleware.LogBuffer) *Handler` are the fx-callable constructors (no more `&auth.Auth{Store: s}` struct literals).
- `newDatabase`, `newSQLDB`, `newLogBuffer`, `newEcho` in `main.go` are small adapter constructors that exist purely to fit fx's DI graph (e.g. fx has no `context.Context` provider, so `newDatabase` fixes `context.Background()` internally rather than the public `database.Open`/`Migrate` signatures taking one from the container).
- `newEcho` wires an `*echo.Echo` but serves it through a plain `*http.Server{Handler: e}` — **echo/v5 has no `Shutdown()` in its public API** (only `Start(addr) error`), so graceful shutdown is implemented by wrapping Echo in a standard `http.Server` and managing `ListenAndServe`/`Shutdown` via `fx.Lifecycle` hooks. This also gives real graceful shutdown on SIGINT/SIGTERM (DB close + HTTP drain), which didn't exist before fx.
- Adding a new handler dependency on the store: add the method to the relevant package's `Store` interface, not to some shared interface — the split is intentional (auth's session/user-lookup surface vs. everything else).

### Backend: persistence (sqlc + goose + libSQL/Turso)

- `internal/store/store.go` is a thin adapter: it holds `*sql.DB` + generated `*dbgen.Queries`, and translates between `dbgen` row structs and `internal/models` structs (handlers/auth only ever see `internal/models` types, never `dbgen` types).
- **Sessions are the one thing NOT in the DB** — `Store` also holds an in-memory `map[string]models.Session` + mutex. Deliberate: avoids a DB round-trip on every authenticated request, sessions have no TTL/eviction logic so a SQL table would just accumulate rows forever. (They are, however, snapshotted to a local JSON file across restarts — see Authentication below.)
- **`lessons.quiz_id` does not exist as a column.** `quizzes.lesson_id` is the single source of truth for that 1:1 relationship (avoids the two tables disagreeing on the FK). `models.Lesson.QuizID` is derived via `LEFT JOIN quizzes` in the `GetLesson`/`GetLessonsForCourse` queries — if you add a new lesson query, remember the join.
- **The lesson view does NOT render the quiz attached via `quizzes.lesson_id`.** It shows only the quizzes the lesson `[[id]]`-links, exactly like its linked files and lessons (`00013_lesson_links_allow_quiz` widened `lesson_links.target_type` to accept `'quiz'`, and `syncLessonLinks` resolves quiz ids). The attached quiz still exists and still surfaces in the course's "Cuestionarios" tab; `GET /courses/:id/lessons/:lessonId` still returns it because `LessonEditor` loads its questions for editing. If a quiz should appear inside a lesson, link it from the lesson body — the editor's "Cuestionario" button does that.
- All entity IDs are app-generated UUIDs (`uuid.NewString()`) inserted by the relevant `Add*` store method — **except `users.id`**, which the caller supplies (guest logins mint their own `g_<hex>` ID; seed data uses literal `"u1"`/`"u2"`/`"u3"`). Don't "fix" `AddUser` to auto-generate — that's intentional.
- Two DB drivers coexist in `internal/database/db.go`, and this is load-bearing, not accidental:
  - `turso.tech/database/tursogo` (pure Go) — used only for **local-only** mode (`TURSO_URL` unset), via `sql.Open("turso", cfg.DBPath)`.
  - `github.com/tursodatabase/libsql-client-go/libsql` (pure Go, HTTP) — used for **remote** mode, via `NewConnector(cfg.TursoURL, ...)`. `tursogo`'s own sync engine only speaks Turso Cloud's CDC protocol and 404s against a self-hosted `sqld`/`libsql-server` (what `config/docker/docker-compose.yml` runs); this driver instead sends every statement as a stateless HTTP request to `sqld`, so there's no local replica file and nothing to keep in sync — `sqld` is the only source of truth, always.
  - This used to be `github.com/tursodatabase/go-libsql`'s CGO embedded-replica connector (a local SQLite file kept in sync with `sqld` via a native replication engine). That combination reliably corrupted the local replica file ("database disk image is malformed") under realistic concurrent write load against this project's (beta) `sqld` image — reproduced in isolation with concurrent `BeginTx`/`COMMIT` bursts even with `SetMaxOpenConns(1)`. Switched to the plain HTTP driver (upstream-deprecated in favor of embedded-replica, but still maintained, and what Turso's serverless/edge SDKs run in production) specifically because it has no local file to corrupt. If a future change reintroduces `go-libsql`, re-verify under concurrent load before trusting it — see git history for the repro harness.
- `sqlc`'s schema source is `internal/database/schema.sql`, a **hand-maintained plain-SQL snapshot** — it does NOT point at `internal/database/migrations/` directly, because goose's `-- +goose Down` blocks are live SQL (`DROP TABLE ...`) that sqlc would also execute while parsing, silently emptying the schema it generates against. When you add a migration, update both files.
- `runSeed`/seeding is **not** part of server startup — `cmd/seed/main.go` is a separate command (`go run ./cmd/seed`), guarded by an empty-check (`GetCourses` count) so re-running it is a no-op once data exists. If a seed run fails partway, it can leave partial rows without tripping that guard (the guard only checks `courses`); a clean retry may need `docker compose down -v` first.
- Insert ordering in `seed.go` matters: rows must be created in FK-dependency order (e.g. a lesson must exist before a user's `CompletedLessons` can reference it via `user_completed_lessons` — real FK constraints are enforced by the remote DB even though a bare local SQLite connection might not enforce them by default).
- `library_items.uploaded_by` stores the uploader's **user ID** (real FK to `users(id)`) — never the display name. `GetLibraryItem`/`GetLibraryItems` resolve it to a name via `LEFT JOIN users` (`uploaded_by_name`) purely for display; `UpdateLibraryItem`'s query does **not** touch `uploaded_by` at all, specifically so round-tripping a fetched `LibraryItem` (whose `UploadedBy` field is now the resolved *name*) back through an update can never write that name into the FK column and violate the constraint.
- Migrations of note: `00001_init`, `00002_add_user_auth` (users.email/password_hash), `00003_remove_lesson_main_file` (drops `lessons.library_item_id` — see "lesson ↔ library item usage" below), `00004_add_server_logs` (server_logs + FTS5, see Observability below), `00014_add_row_versions` (the `(hlc, origin_node)` pair, see below).
- **Lessons have no stored link to library items.** The old `lessons.library_item_id` "main file" column was removed. Which lessons embed a given `library_items.id` is answered live via `store.GetLessonsUsingLibraryItem`, a `LIKE '%[[id]]%'` scan over `lessons.content_text` (the same `[[id]]` wiki-link syntax the frontend already parses) — there is no junction table to keep in sync, so deleting/editing a lesson is automatically reflected with zero extra bookkeeping. `GET /library/:id/usage` exposes this to `LibraryDetail.tsx`.
- Multi-statement SQL in a migration (e.g. `CREATE TRIGGER ... BEGIN ... END;`) **must** be wrapped in `-- +goose StatementBegin` / `-- +goose StatementEnd` — goose splits migration files on bare `;` otherwise, which truncates the trigger body mid-statement and fails with a cryptic SQLite parser error.
- sqlc + SQLite gotcha: don't mix `sqlc.narg(...)` (named, numbered `?N` placeholders) with plain unnumbered `?` in the same query (e.g. narg'd `WHERE` filters plus plain `?` for `LIMIT`/`OFFSET`) — sqlc's sqlite codegen numbers them inconsistently with the Go argument order it generates, silently binding the wrong value to the wrong placeholder. Fix: once a query uses any `sqlc.narg`, give **every** parameter a name via `sqlc.arg('limit')`/`sqlc.arg('offset')` too, so the whole statement uses one consistent numbering scheme. See `queries/server_logs.sql` for the working pattern (optional filters via `COALESCE(sqlc.narg('x'), col)`, never referencing the same narg twice in one condition, which also avoids a separate sqlc numbering bug).
- **Keep sqlc query comments ASCII.** A non-ASCII character in the comment above a query silently truncates the generated SQL by the extra bytes — an em dash in one comment produced `SELECT id, file_path FROM library_ite`, which then fails at runtime with `incomplete input`. Nothing warns you: `sqlc generate` succeeds and the Go compiles. All the query files are ASCII today; `grep -rnP '[^\x00-\x7F]' internal/database/queries/` should stay empty.
- FTS5 `MATCH` inside a query sqlc has to parse must be column-qualified (`server_logs_fts.message MATCH ?`), not the bare `table MATCH ?` form — both are valid SQLite, but sqlc's parser only accepts the qualified form.
- **Content backup (`internal/store/backup.go`) is the one place that bypasses sqlc entirely**, on purpose: `ExportTables`/`ImportTables` reflect over `sqlite_master` + `SELECT *` and exchange `[]models.TableDump` (column-name → value maps), so a table added by a future migration is included with zero extra code. Tables are inserted in **FK-dependency order, topologically sorted from `pragma_foreign_key_list`** — *not* in `sqlite_master.rowid` (creation) order. Creation order looks equivalent and isn't: `00006_decouple_quizzes` rebuilds `quizzes` with SQLite's DROP + RENAME dance, which moves it to the end of `sqlite_master`, *after* the `quiz_questions` that reference it — inserting in that order dies with `FOREIGN KEY constraint failed` on a real migrated DB. `PRAGMA defer_foreign_keys = ON` is set on the import tx as a belt (it also covers `forum_posts.parent_id` self-references), but the ordering alone satisfies every cross-table FK. `skippedTable` excludes `sqlite_*`, `goose_db_version` (migrations are applied on boot, never restored), `server_logs*`, and everything `sync_*` — those are this node's own operational state, not shared content. Letting a peer write into them through an import would also be a hole: `ApplyOps` uses the same list as its whitelist.
- **`ImportTables` merges, it never wipes — and collisions are resolved by row version, not by who got there first.** Every table with mutable rows carries `(hlc, origin_node)` (migration `00014`, see "row versioning" below); an incoming row overwrites the local one when its pair is greater, and is dropped otherwise. Re-importing the same zip is still a no-op (equal versions aren't greater). It returns per-table `models.TableImport{Applied, Skipped}` counts — `Applied` covers inserts *and* overwrites — all in one transaction. The junction tables (`course_enrollments`, `user_completed_lessons`, `forum_likes`, `*_links`) have no version columns on purpose: they're set membership, so their only conflict is insert-vs-delete, which needs an operation log rather than a version column. They keep the old skip-on-collision behaviour.
- **Don't write the merge as `INSERT OR IGNORE ... ON CONFLICT DO UPDATE`.** It parses, runs, and silently does nothing on a conflict — the `OR IGNORE` swallows it before the upsert is reached (verified against this project's driver: 0 rows affected, row unchanged; the same statement without `OR IGNORE` updates). But `OR IGNORE` can't just be dropped either: it's what stops a collision on a *non-key* UNIQUE (two nodes that independently created the same student → same `users.email`, different id) from aborting the entire import. So `insertRows` classifies rows in Go first — new rows go in with `INSERT OR IGNORE`, rows already present locally take the plain upsert path (`storedVersions` reads the local versions in one query per table). The upsert still repeats the comparison in its `WHERE` as a belt.
- Known ceiling, unchanged: a row skipped because it collides on a non-PK UNIQUE leaves its dependent rows pointing at a parent id that isn't there, and the FK error aborts the whole import — loud, not silent. Fixing it properly means id remapping, which nothing needs yet.
- `seeds/` holds a hand-built **content** backup (`radix-seed-backup.zip`, 9 asignaturas / 36 lecciones / 45 cuestionarios / foro / 35 archivos) plus the generator that produces it (`build_seed_backup.py` + `seed_content.py`, all the prose lives in the latter). It's importable through the normal backup endpoint and is **not** a replacement for `go run ./cmd/seed`. Media is resolved from Wikimedia Commons and YouTube through `media.lock.json`/`youtube.lock.json` so re-runs are reproducible; nothing uses an RNG (grades/enrolments derive from a CRC of the ids). `backend/internal/handlers/seedzip_test.go` imports that zip through the real `readDumps` → `ImportTables` path and asserts the content landed — it fails if a migration drifts from the zip, which is the signal to regenerate. See `seeds/README.md`.
- `GET/POST /api/v1/backup/export|import` (admin-only) wrap the above in a zip (`manifest.json`, `data/<table>.json`, `uploads/`) — see `internal/handlers/backup.go`. The extracted folder is the same layout, so a dump can be edited by hand and re-imported. `internal/store/backup_test.go` covers the round-trip, both merge paths, and the FK ordering above; it builds its schema from `schema.sql` instead of `database.Migrate` because the local-only `tursogo` driver rejects `00003`'s `DROP COLUMN` and has no `fts5` module.
- `cmd/flush` (`store.ClearTables`) empties every table in **reverse** FK-dependency order, in one transaction, leaving the schema and `goose_db_version` intact — it's the "start over" counterpart to `cmd/seed` and to importing a backup. It wipes `server_logs` and the `sync_*` tables too (flushing this node means flushing its history and its cursors), which is why `skippedTable` is now split: `internalTable` is what nothing may ever touch, `skippedTable` adds the backup-only exclusions. It also deletes `sessions.json` so a restarted server can't restore tokens for users that no longer exist.
- **`tursogo` segfaults on `DELETE` with `foreign_keys = ON`** (inside `turso_connection_prepare_first`, during cgo) for the full-schema + rows + transaction case — reduced repros don't trigger it, and the same statements are fine with the pragma off, which is that driver's default. So `TestClearTables` deliberately runs without FK enforcement and says so; don't "fix" it by adding the pragma. Only local-only mode is affected — remote mode goes over HTTP with no cgo at all.
- **Any test that touches referential integrity must `PRAGMA foreign_keys = ON` first.** `tursogo` opens with `foreign_keys = 0` while the remote `sqld` the app actually runs against enforces them — so an FK-violating import passed the whole suite and still failed in the browser. Both backup tests now assert the pragma took effect before trusting anything (the local driver's `SetMaxOpenConns(1)` is what makes a connection-scoped pragma stick).

### Backend: row versioning (multi-node merge)

How two edge servers agree on the result when they've both edited the same row. The transport that moves those edits is the operation log, below.

- **Every table with mutable rows carries `(hlc, origin_node)`** (`00014_add_row_versions`): `users`, `courses`, `library_items`, `lessons`, `quizzes`, `quiz_questions`, `quiz_grades`, `forum_posts`. Junction tables deliberately don't — see the `ImportTables` bullet above.
- `internal/clock.HLC` is a **hybrid logical clock**: `Now()` returns `max(wall clock millis, last+1)`, so the sequence is monotonic no matter what the clock does, while still tracking real time closely enough to be readable in a dump. This is not decoration: an edge server is a Pi with no RTC and, by design, no internet, so no NTP — its clock drifts and can come back from a power cut far behind. A plain `time.Now()` version column would then resolve conflicts backwards, and the lagging node would lose every edit it made. Don't "simplify" it to a timestamp.
- `Observe(v)` folds in a value seen elsewhere, and that's what carries causality: after importing a peer's rows (`ImportTables` calls it with the highest version seen, after the commit) this node's next write is guaranteed to sort after everything it just learned.
- **`store.SeedClock` must run before the first write of a process** (wired in `main.go`'s `newStore` and in `cmd/seed`). It reads `MAX(hlc)` per versioned table so a restart with a rewound clock can't stamp new rows below the node's own older ones.
- `Store.version()` is the single stamping point; every `Add*`/`Update*` calls it exactly once, so all rows written by one logical operation share a version. `store.New` now takes the node id (`cfg.NodeID`, default hostname).
- Everything in `internal/store/version.go` is derived from the live schema via `pragma_table_info` — same spirit as backup.go's FK ordering. A table added by a future migration takes part automatically if it has the two columns; there's no list to keep in sync.
- `origin_node` only breaks an exact tie on `hlc`. It exists so the outcome is identical on every node instead of depending on which one merged first: "keep mine on a tie" looks consistent and actually diverges, since each node would keep its own value forever. `TestTieBreakConvergesRegardlessOfOrder` pins that down.
- Rows imported from a dump with no version columns (the `seeds/` zip, built before `00014`) land with `hlc = 0`, i.e. they lose to anything anyone actually wrote. That's intended — nobody can say when that content was authored — and it doesn't need the zip regenerated.

### Backend: peer synchronisation (the DTN queue)

`sync_log` is gone (migration `00015`). It held human-readable audit strings and `POST /monitor/sync` deleted them and reported success — nothing was ever sent anywhere. What replaced it:

- **`sync_ops` is an outbox of replayable operations** — `(seq, origin_node, table_name, pk_json, op, hlc, payload, label, created_at)`. `payload` is the whole row for an `upsert` (never a diff) and empty for a `delete`.
- **Identity is `(origin_node, table_name, pk_json, hlc)`, not `seq`**, with a UNIQUE index behind it and `INSERT OR IGNORE` in front of it. That's the idempotency: applying an op twice, or receiving one that came back around a loop, does nothing.
- **`seq` is local and is the cursor domain.** An op learned from a peer is stored with its ORIGIN preserved and a fresh local `seq`, which is what makes ops forward: A → B → C converges without A and C ever meeting (`TestOpsForwardAlongAChain`).
- **Ops are written in the same transaction as the data** (`store.logUpsert`/`logDelete`, called from every `Add*`/`Update*`). That's why `withTx` hands over the raw `*sql.Tx`: `logUpsert` reads the row back with `SELECT *` so the payload always matches what an export would produce, with no per-table column list to maintain. An op committed without its data, or data without its op, is a change that either never happened or never propagates.
- **Labels are derived** from the row's `title`/`name` column, not passed in. The 13 hand-written `EnqueueSync(ctx, "ADD_LESSON: "+title)` calls in the handlers are gone.
- **Deletes are ops, so there is no tombstone table.** The log itself is the tombstone: `applyUpsert` checks `CountDeletesNotOlderThan` before writing, so an older edit arriving after a delete can't resurrect the row (`TestADeletedRowIsNotResurrected`). Delete-then-reinsert patterns must log the removals — see `replaceQuizQuestions` (a quiz edit mints fresh question ids, so a peer that only got the new ones would show old and new side by side) and `setCompletedLessons`.
- **The `[[id]]` link tables are NOT shipped as ops.** They're a pure function of the content, so `ApplyOps` re-derives them locally (`rederive` → `syncLessonLinks`/`syncQuizLinks`/`syncForumLinks`). Same reasoning as `ON DELETE CASCADE` rows, which also aren't logged: deterministic derivation costs nothing to redo and can't drift.
- **Transport is pull, over one read-only route**: `GET /api/v1/sync/ops?since=&limit=&node=`. `internal/dtn` is the puller (`Syncer.Round` per peer, cursor in `sync_peers` keyed by URL). Pull keeps all cursor state on the asking side and lets whichever node has power and signal initiate. There is deliberately **no backoff** — the peer being unreachable is the normal state here, not an error to back away from.
- **The puller sends its own cursor, so acknowledgement is free**: the server records it in `sync_readers`, and "pending" on the Monitor means *not delivered anywhere* rather than *not yet deleted*. That's what makes the queue drain visibly when a peer comes back.
- **Auth is a shared `SYNC_TOKEN`, not a session** — `handlers.GetSyncOps` compares it with `subtle.ConstantTimeCompare`, an empty token closes the endpoint, and `auth.Middleware` skips that one path. It's read-only by design: a peer can pull and decide what to apply, never write. The token travels in the clear over HTTP, which is fine on a trusted LAN and not beyond it.
- **A backup import also emits ops** (`logImportedRow`), keeping each row's own version and origin. Otherwise content imported on the central server would stop there. The zip's remaining jobs are what a delta can't do: bootstrapping a node with no history, and sneakernet.
- **Files travel separately from their rows.** An op ships the `library_items` row, not the bytes, so after applying ops `dtn.Syncer.fetchFiles` compares the library inventory (`store.LibraryFiles`) against `uploads/` and downloads what's missing from `GET /api/v1/sync/file/:id` (same sync token, same `serveFile` as the user-facing route). It works from the whole inventory rather than from the ops just applied, deliberately: that also repairs a transfer the link cut in half, and a node restored from a zip with a pruned uploads folder. Downloads land on a temp file and are renamed, so a half-transferred video never looks complete. The file client has **no timeout** — a video over a village link legitimately takes minutes.
- `library_items.file_path` is stored **relative to the process working directory** (`handlers.UploadsDir`), and that's load-bearing now: the path travels inside the op payload, so every node has to resolve the same stored string to its own copy. The writer still runs it through `filepath.Base`.
- **Ceilings, both deliberate:** ops are never pruned (pruning means deciding a peer will never return; a node offline longer than the retention would have to re-bootstrap from a zip), and an op that trips a constraint is skipped rather than aborting the batch — it retries on every later pull, since nothing marks it consumed.
- **Local two-node setup** is documented in the README ("Dos nodos en una máquina"): `docker compose --profile peer up -d` for the second sqld, `ENV_FILE=.env.b go run ./cmd/server` for the second backend (that's what `ENV_FILE` exists for).

### Backend: containers and the test network

- `backend/Dockerfile` and `frontend/Dockerfile` exist **only** for `config/docker/testnet.yml`. They are not production images: no data, no volumes, everything writable is ephemeral.
- The backend builds with `CGO_ENABLED=0` — both drivers are pure Go, and the containers use remote mode anyway. The runtime image carries ffmpeg for `ffprobe` (upload metadata).
- `backend/docker-entrypoint.sh` seeds and then execs the server. **The seed is the readiness check**: it opens the database and runs the migrations, so if it succeeds sqld is up and the schema is current — one thing that has to work anyway, rather than a health probe that could disagree with it. It retries for 60s.
- Seeding uses **`cmd/seed -zip <path>`**, which imports a content backup straight through `store.ImportTables` with no server running, no HTTP and no admin login. That's why the zip reader moved out of `handlers` into **`internal/backupzip`** (`ReadDumps`, `RestoreUploads`, and `UploadsDir` — now the single definition of where library files live, shared by the upload handler, the backup import and the peer file download).
- The frontend image is nginx serving the built SPA plus a `/api/` proxy to that node's backend (the Vite proxy is dev-only). `nginx.conf.template` goes through the image's envsubst at startup so one image serves every node via `BACKEND_URL` — which is why **the template must not use any nginx variable**: `$uri` would be substituted to empty. SPA routing is `error_page 404 =200 /index.html` for exactly that reason, not `try_files`.
- Both nodes import the same zip, whose rows carry `hlc = 0` / empty origin. Their op identities are therefore identical on every node, so the first sync round pulls them and skips them all. Harmless, and it's why the Monitor shows a large pending count for the first few seconds.
- `config/docker/docker-compose.yml`'s `peer` profile is a different thing and stays: a second *database* for running two backends on the host with hot reload. The testnet is for seeing it work; the peer profile is for working on it.

### Backend: authentication

- Real email+password login (`bcrypt`), not the original role-picker demo. `auth.Login` looks up `Store.GetUserByEmail` and compares with `bcrypt.CompareHashAndPassword`; both "no such user" and "wrong password" return the same generic 401 (`invalid email or password`) so the endpoint doesn't leak which emails exist.
- Guest access is a **separate** endpoint, `POST /api/v1/auth/guest` (`auth.LoginGuest`) — no credentials, mints a `g_<hex>` user on the fly with a synthetic `<id>@guest.local` email (needed only to satisfy `users.email`'s `UNIQUE NOT NULL` constraint, never actually used to log in). Both `/auth/login` and `/auth/guest` are excluded from `Auth.Middleware()`'s bearer-token check, same as before.
- Seed users (`cmd/seed/seed.go`) all share one bcrypt-hashed password (`seed.SeedPassword`, currently `radix2024`) computed once and reused for all three accounts — only the email differs. See the README's credentials table.
- **Sessions now survive process restarts.** `store.SaveSessions`/`LoadSessions` (de)serialize the in-memory session map to `<DB_PATH dir>/sessions.json` (gitignored). `main.go`'s `newStore` loads it on `OnStart` and saves it on `OnStop` via `fx.Lifecycle` — this is a deliberate compromise: keeps the original "sessions never touch the DB" design (see below) while fixing the real pain point (every `air` hot-reload during dev was silently logging everyone out). It does **not** add a TTL/eviction — that's a separate, still-open concern.
- **Request contexts are detached from cancellation.** `middleware.DetachContext` (wired first in `newEcho`'s middleware chain) replaces `c.Request().Context()` with `context.WithoutCancel(...)` before any handler runs. Without this, a client disconnect/navigation-away mid-write cancels the context a handler's DB transaction is built from — which wedges the shared connection and was a second, independent cause of the corruption described above (on top of the driver swap). Verified empirically: a cancel/write loop against `sqld` corrupted in under 1,000 cycles without this middleware, 1,000+ cycles clean with it.

### Backend: consistent HTTP responses

`internal/httpx` centralizes response shapes — `httpx.OK(c, status, data)` and `httpx.Fail/NotFound/BadRequest/InternalError/Forbidden/Unauthorized/NoContent(c, ...)`. This is **not** a new envelope: success responses are still the raw payload (array/object), errors are still `{"error": "..."}` — same shape the frontend's `lib/api.ts` already expects (`err.error` on non-2xx). Every handler should use these instead of hand-rolling `c.JSON(status, map[string]string{"error": ...})`.

### Backend: logging & observability

- All logging goes through `go.uber.org/zap`, not the stdlib `log` package (except one truly-pre-app-startup `log.Fatal` in `main()`, before any logger exists). There are two logger tiers, and the split exists to break a real dependency cycle, not for style:
  - `middleware.NewBaseLogger()` — console-only (`zapcore.NewConsoleEncoder` → stdout), zero dependencies. Used only by `store` (session-load errors) and `LogPersister` itself (its own flush/cleanup failures) — anything constructed *before* the full logger can exist.
  - `middleware.NewLogger(base, buffer, persister)` — wraps base with `zapcore.NewTee(consoleCore, observabilityCore)`. **One `logger.Info()`/`logger.Error()` call anywhere in the app now drives three things at once**: stdout, the in-memory live-tail (`LogBuffer`, powers `GET /logs` and the Logs page's "En vivo" panel), and the durable `server_logs` table (async, via `LogPersister`). Built once in `newEcho` and used for the HTTP request logger (`middleware.GoServerLogger`) plus the server start/stop messages — anything logged through it is expected to show up in the observability UI.
- `server_logs` deliberately has **no per-source columns** (no `method`/`path`/`role`/`status`) — only `timestamp`, `level`, `message`, and `fields` (a JSON blob). `observabilityCore.Write` captures *whatever* zap fields the call site attached, generically, via `zapcore.NewMapObjectEncoder()` + `field.AddTo(enc)` — this table isn't HTTP-request-specific, it's meant for every log call in the app, and different call sites can attach completely different fields. `message` is always a human-authored, meaningful string (never blank) specifically so FTS5 full-text search over it stays useful; structured data that a caller wants to filter/inspect goes in `fields`, but `fields` itself is **not** currently wired into any `WHERE` clause (json_extract-based filtering was considered and dropped — see git history — in favor of keeping the schema source-agnostic). Filtering today is level + timestamp range (real columns) + free-text search over `message`.
- `middleware.LogPersister` batches entries and flushes on a ticker (3s or 50 entries, whichever first) instead of writing per log call — `Enqueue` is a non-blocking channel send that silently drops the entry if the buffer's full, so a slow/down DB can never add latency to a request or a log call. It also runs the `LOG_RETENTION_DAYS` (default 30) cleanup, once on startup and then every 24h.
- `server_logs_fts` is an FTS5 external-content table over `message`, kept in sync purely by SQL triggers (`server_logs_ai`/`server_logs_ad`) — the Go code never writes to it directly.

### Frontend

- `src/types/index.ts` mirrors the Go structs by hand — when a backend model or response shape changes, update this file too (no codegen link between them). `src/lib/api.ts` is the single fetch client: it injects the bearer token from `localStorage`, and throws on non-2xx using the `{error}` body.
- **All server state goes through TanStack React Query** via the domain hooks in `src/hooks/` (`useCourses`, `useLibrary`, `useLessons`, `useQuizzes`, `useForum`, `useMonitor`, `useLogs`) — components never call `api.*` directly inside `useEffect`. Mutations invalidate (or optimistically update — see `useToggleForumLike`) the relevant query keys themselves; don't add manual `load()`-style refetch callbacks after mutations. Polling (Monitor 3s, live logs 1.5s) is `refetchInterval` on the hook; Logs history pagination is `useInfiniteQuery`. Query keys follow the REST nesting: `["courses", id, "students"]`, `["library", id, "usage"]`, etc. — new hooks should match. Auth (`context/AuthContext.tsx`) deliberately stays outside React Query (localStorage-backed, no bootstrap fetch).
- **UI is shadcn-style primitives** in `src/components/ui/` (button/card/badge/input/textarea/label/select/dialog/tabs/table/progress/separator/sonner), imported per-file via the `@/` alias (`@/components/ui/button`). Colors are semantic CSS-variable tokens defined in `src/index.css` + `tailwind.config.js` (`bg-background`, `text-foreground`, `text-muted-foreground`, `bg-card`, `border-border`, `primary`, `secondary`, `destructive`, `success`, `warning`) — never raw `slate-*`/`indigo-*`/`emerald-*` palette classes in app code (`lib/rbac.ts`'s role colors are the one grandfathered exception). Errors/success surface via `sonner` toasts (`toast.error/success`), never `alert()` or hand-rolled banners. Radix `Select` items can't have `value=""` — use an `"all"` sentinel mapped to `undefined` (see `pages/admin/Logs.tsx`).
- **Both themes exist and every colour must come from a token.** `:root` in `index.css` is the **light** palette, `.dark` overrides it with the dark one, and Tailwind's `darkMode: ["class"]` keys off that class on `<html>`. `context/AppearanceContext.tsx` owns four persisted preferences (theme `auto|light|dark`, text size, reading width, nav placement) and is the only thing that touches the class; the inline script in `index.html` applies the stored theme before first paint so a dark-theme user gets no white flash. `auto` follows `prefers-color-scheme` live, not just on load. Hardcoding a colour now breaks one of the two themes — the video containers' `bg-black` is deliberate (a letterbox reads black either way).
- `components/common/AppearancePanel.tsx` is the Wikipedia-style panel (Texto / Anchura / Color); it is the right rail of `ReadingLayout` and nothing else renders it. The header carries a compact theme cycle too, so the theme is reachable from screens with no reading rail. The preferences are global, not per-lesson.
- **There is no vertical nav rail — the navigation lives in the `Header`**, rendered by `components/layout/NavItems.tsx` from `getNavItems` (which is where the role filtering stays). The old `Sidebar.tsx` and the `navMode` preference that toggled it are gone; don't reintroduce a left nav column. The header's subtitle and "Edge activo" chip are `xl`-only, since below that the links need the room.
- **`components/layout/ReadingLayout.tsx` owns the lesson/quiz reading layout** and both viewers must go through it. One `lg` grid, three equal-width-railed columns and two rows:
  `[ índice y enlaces ] [ contenido ] [ apariencia ]` — the rails match in width so the content column is centred against the viewport rather than pushed left, and the reading matter is flanked by navigation on one side and controls on the other.
  Row 1 holds only the `header` prop (back link, title, Editar) in the middle column; that's what makes the rails start level with the content instead of level with the back link. Row 2 is rail · content · rail. Reading width is a track swap (`48rem` cap vs `1fr`) with the rails fixed at `16rem`, not a `max-w-*` on the column. `justify-center` is `lg`-only because below that there is one implicit column that centring would shrink to its content, and the rails carry `self-start` so the grid doesn't stretch them and kill the inner `sticky`.
- **`prose`/`prose-invert` are not real here** — `@tailwindcss/typography` was never installed, so those classes did nothing and rendered markdown had no styling at all. Lesson/quiz/forum content uses the `.reading` block in `index.css` instead, with `.reading-{small,standard,large}` supplying `--reading-font`. Everything inside `.reading` is sized in `em` on purpose: that's what makes the text-size preference scale headings, lists and tables together instead of only paragraphs. Don't reintroduce `prose*` classes without actually adding the plugin.
- The CodeMirror theme (`MarkdownEditor.tsx`) reads the same tokens via `hsl(var(--foreground))` etc. CodeMirror can't see Tailwind classes but it does resolve `var()` in a CSS value, so there's no second palette to maintain — only its `dark` flag is passed from `useAppearance`, for the styling CodeMirror decides on its own. Picker modals (`components/common/*Modal.tsx`) are Radix `Dialog`s mounted-when-open: `<Dialog open onOpenChange={(o) => !o && onClose()}>`.
- **Every "volver" affordance is `components/common/BackLink`** — never a hand-rolled `<Link to={...}>` back to a guessed parent. It calls `navigate(-1)`, so a library file opened from a lesson returns to that lesson instead of the library index. Its `fallback` prop is used *only* on direct entry (shared link, new tab), detected via react-router's `history.state.idx === 0` (`location.key` is not usable here: it resets to `"default"` on reload, where real history does exist). The label is always "Volver atrás" in both branches, so the two paths are indistinguishable to the user.
- `src/lib/markdown.ts` + `codemirror-wiki.ts` implement the `[[id]]` wiki-link syntax used inside lesson content to embed library items — the editor (`MarkdownEditor.tsx`) highlights these and shows a hover preview; `InlineMedia.tsx` renders the embedded result by file type (video/audio/image/pdf/text/document).
- Two different components render a library file and they are not interchangeable: `InlineMedia.tsx` is the full embed (player with controls, PDF iframe, whole text file) used inside lesson/quiz/forum content, while `LibraryPreview.tsx` is the thumbnail used in list views (`pages/Library.tsx` cards, `FilePickerModal` rows) — real image, first video frame, first 400 bytes of a text file, icon for audio/pdf/document. It decides "does this item have a file at all?" from `originalFilename`, because `LibraryItem.FilePath` is `json:"-"` and never reaches the client; a legacy metadata-only item has neither.
- `ServeLibraryFile` uses `http.ServeContent`, not a plain `io.Copy`/`c.Stream`, **because Range requests are load-bearing**: without them a `<video>` can't seek at all, `LibraryPreview` can't pull just the first frame, and the text thumbnails would download whole files. Content-Type is set from the stored mime type before the call, which is also why the name argument is empty (a non-empty name would make ServeContent re-sniff).
- **There is one admin page**, `pages/admin/AdminPanel.tsx`, with three tabs: General (crear curso / vincular recursos), Monitor and Logs. `components/admin/MonitorPanel.tsx` (disk/sessions/DTN queue/backup) and `components/admin/LogsPanel.tsx` (live tail + filterable history + stats) are those tabs' bodies — components, not routes, which is why they live under `components/` and render no `<h1>` of their own. They stay two distinct components with separate concerns: don't merge the log UI into MonitorPanel. The active tab is in `?tab=` (same pattern as `CourseDetail`), Radix unmounts the inactive tab so neither panel keeps polling while hidden, and `/admin/monitor`/`/admin/logs` survive only as `<Navigate>` redirects for old bookmarks.

## Environment variables (`backend/.env`)

| Variable | Purpose |
|---|---|
| `PORT`, `LOG_BUFFER_SIZE`, `CORS_ORIGINS`, `ENVIRONMENT` | server basics |
| `LOG_RETENTION_DAYS` | days to keep rows in `server_logs` before `LogPersister` prunes them (default 30) |
| `SYNC_PEERS`, `SYNC_TOKEN`, `SYNC_INTERVAL_SECONDS` | peer synchronisation: comma-separated peer base URLs to pull from (empty = standalone node), the shared secret guarding `GET /sync/ops` (empty closes it), and how often a round runs (default 60s) |
| `ENV_FILE` | which env file to load (default `.env`) — lets a second node run from the same checkout |
| `NODE_ID` | this edge server's identity, stamped as `origin_node` on every row it writes and used to break version ties on merge (default: hostname) |
| `DB_PATH` | local file used as SQLite storage (local-only mode only — remote mode keeps no local cache); its directory also holds `sessions.json` |
| `TURSO_URL`, `TURSO_AUTH_TOKEN` | if `TURSO_URL` is set, the backend connects in remote mode against that libSQL-compatible server (defaults to the local docker-compose container, no auth token needed there) |
| `GOOSE_DRIVER`, `GOOSE_DBSTRING`, `GOOSE_MIGRATION_DIR` | for the `goose` CLI only (manual migration authoring/status) — the app itself runs migrations programmatically from the embedded `migrations/` folder and doesn't read these |

## University deliverable reports (`docs/`)

When asked for a report/document for university submission (requirements spec, design doc, any "informe"), follow this process — `docs/ESPECIFICACION_REQUISITOS.md` is the reference example:

1. **Author the content as a markdown file in `docs/`** (UPPER_SNAKE name, e.g. `docs/DISENO_ARQUITECTURA.md`), in Spanish, then generate the PDF:
   ```bash
   python3 docs/tools/md2pdf.py docs/ARCHIVO.md --title "Título del documento — RADIX"
   ```
   Output: cover page from `docs/PORTADA.png` + auto-generated clickable "Índice" with real page numbers + body with page numbers in the footer, PDF Creator/Producer metadata blanked. Requires chromium, poppler (`pdfinfo`/`pdftotext`), python-markdown; ffmpeg optional (recompresses the cover, ~4x smaller PDF).

2. **Markdown conventions the script depends on:** no document title and no cover content in the `.md` — the file starts directly at `## 1. Introducción`. Sections are `##` and subsections `###`; exactly those two levels feed the TOC. Long heading texts are fine (page detection is whitespace-normalized). GFM tables supported.

3. **Team members:** `docs/INTEGRANTES.md` is the source of truth (docente, C.I., which of the two asignaturas — Sistemas Distribuidos / Robótica — each student belongs to). When a report needs an integrantes list, filter that table by the relevant asignatura; resolve any `REVISAR`/`PENDIENTE` HTML comments in it with the user before including those rows.

4. **Content/style rules for these documents:**
   - Formal academic Spanish, but slightly imperfect on purpose — natural student writing, not polished-perfect prose. Avoid em-dash-heavy sentences, rhetorical parallelism, and showy vocabulary. No spelling/grammar errors.
   - **Never mention Claude, AI, or code assistants** anywhere in content or metadata (don't cite `CLAUDE.md` as a reference — cite `README.md`, IEEE standards, textbooks like Tanenbaum & Van Steen / Coulouris instead).
   - Requirements docs follow adapted IEEE 830 structure with `RF-XX`/`RNF-XX`/`RES-XX` ID tables; when theory is requested, it goes in its own section *before* the system-specific content, each concept tied back to RADIX.
5. **Verify before delivering:** Read a few pages of the generated PDF visually (cover, índice, one body page), and check the script's output line — it prints a `SIN PÁGINA EN ÍNDICE` warning if any heading couldn't be located.

**Never post-process the PDF with `pdfunite`** (or any merge tool): merging destroys the named destinations that make the índice links work. The cover must go through the script (it embeds the PNG in the same single Chromium render). That's also why the script exists at all — don't replace it with pandoc/pdfunite pipelines.
